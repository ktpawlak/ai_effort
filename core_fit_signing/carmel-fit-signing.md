# Ubuntu Core: signed FIT/DTB for Qualcomm — what it is and whether Launchpad can do it

Analysis of the DTB signing step in the Carmel (Dragonwing) Ubuntu Core kernel
snap, and whether Launchpad supports that signing in its current form.

**Source:**
[`canonical/carmel-image` `kernel/dragonwing/core26/snap/snapcraft.yaml:217`](https://github.com/canonical/carmel-image/blob/cabee7af03c6713b6fe01631a48dda68b4103dbf/kernel/dragonwing/core26/snap/snapcraft.yaml#L217)
(commit `cabee7af`). Written 2026-09-29.

> **Separate workstream from the DTB capsule work** in
> `~/qualcomm/ai_effort/capsule_update/`. The two are easy to conflate — both
> involve Qualcomm, DTBs, FIT images and detached PKCS#7/CMS signatures — but
> they have different consumers, different trust anchors and different
> blockers. Section 5 contrasts them.

---

## 1. What the snippet actually does

From the `combined-dtb` part:

```sh
"${CRAFT_PART_SRC}"/build-dtb-image.sh \
    --soc hamoa purwa qcs6490 qcs8275 qcs9075 \
    --dtb-src "${CRAFT_STAGE}"/dtbs/qcom/ \
    --out "${CRAFT_PART_BUILD}"/combined-dtb.bin \
    --prune

# Extract the dtb from the vfat image generated by the script so that a
# signature can be generated
mcopy -i "${CRAFT_PART_BUILD}"/combined-dtb.bin ::qclinux_fit.img .

openssl cms -sign \
  -inkey  /usr/lib/ubuntu-core-initramfs/snakeoil/PkKek-1-snakeoil.key \
  -signer /usr/lib/ubuntu-core-initramfs/snakeoil/PkKek-1-snakeoil.pem \
  -binary \
  -in  "${CRAFT_PART_BUILD}"/qclinux_fit.img \
  -out "${CRAFT_PART_BUILD}"/qclinux_fit.sig \
  -outform DER

# Copy the signature into the vfat image
mcopy -i "${CRAFT_PART_BUILD}"/combined-dtb.bin \
  "${CRAFT_PART_BUILD}"/qclinux_fit.sig ::
```

Sequence: build the FAT image, pull `qclinux_fit.img` back out, sign it, drop
the `.sig` back in beside it.

Result on the FAT volume:

```
combined-dtb.bin  (FAT)
├── qclinux_fit.img     ← the FIT, byte-for-byte unmodified
└── qclinux_fit.sig     ← detached CMS signature, DER
```

### This is not U-Boot FIT signing

Worth stating plainly, because the terminology collides badly:

| | U-Boot FIT signing | What Carmel does |
|---|---|---|
| Tool | `mkimage -k <keydir> -r` | `openssl cms -sign` |
| Requires | `signature {}` nodes in the `.its` | nothing in the FIT |
| Covers | individual image nodes | the whole `.img` blob |
| Output | modifies the FIT **in place** | separate `.sig` **sidecar** |
| Verifier | U-Boot | Qualcomm UEFI firmware |

The FIT is an opaque blob here. Nothing inside it is signed or hashed
individually.

### Signature properties

`openssl cms -sign` with no `-nodetach`, no `-nocerts`, no `-noattr`:

- **detached** — content not embedded (it is the separate `.img`)
- **certificates embedded** — signer cert travels inside the CMS blob
- **signedAttrs present** — signature covers the attributes, not raw content
- **DER**, default digest (sha256 in current OpenSSL)

Structurally the same shape as the capsule's PKCS#7. See
`~/qualcomm/ai_effort/capsule_update/capsule-binary-layout.md` section 2.

### The key

`PkKek-1-snakeoil.key` from `ubuntu-core-initramfs` — a **test key**, shipped
for development. The in-file comment states the real requirement:

> *"This should be signed with the same key as the UKI generated by the initrd
> plugin."*

`PkKek` = Platform Key / Key Exchange Key — i.e. the **UEFI Secure Boot key**.
The `initrd` part (`:157-181`) sets `initrd-build-efi-image: true` and stages
`kernel.efi`, the UKI. Qualcomm firmware verifies the FIT signature as part of
the same Secure Boot chain that admits the UKI, per the referenced Qualcomm
doc `80-70020-11` ("Enable UEFI secure boot").

So: **snakeoil works for development; production needs whatever real key signs
the UKI.**

## 2. Does Launchpad support this today?

**No.** And the reason is in two layers, the second more important than the
first.

### Layer 1 — no archive signing mode produces this format

`lib/lp/archivepublisher/signing.py`:

| Mode | Implementation | Why it does not fit |
|---|---|---|
| `.efi` UEFI | `sbsign --key --cert` | PE/COFF only. Tested against a capsule-shaped file: `Invalid DOS header magic`, exit 1. A FIT is not a PE either. |
| `.fit` FIT | `mkimage -F -k <dir> -r <img>` (`:683-697`) | **Name collision.** In-place U-Boot node signing — the wrong mechanism, and it would modify the FIT that must stay untouched. |
| `.ko` KMOD | `kmodsign -D sha512 <pem> <x509> <img> <img>.sig` (`:636-645`) | Closest shape (detached, `.sig` sidecar) but the certificates and signed attributes are stripped — **verified empirically, see below**. |

#### Verified: `kmodsign` vs `openssl cms`

Note that LP uses **`kmodsign`** (from `sbsigntool`), *not* the kernel's
`scripts/sign-file`. They are different tools, so the comparison below was run
against `kmodsign` directly rather than inferred from `sign-file.c`. Same
2048-bit key and 4096-byte input for both:

```sh
kmodsign -D sha512 k.pem c.der blob.bin blob_D.sig     # what LP does
openssl cms -sign -inkey k.pem -signer c.pem \
    -binary -in blob.bin -out carmel.sig -outform DER  # what Carmel needs
```

| Property | `kmodsign -D` | `openssl cms -sign` |
|---|---|---|
| Output size | **436 B** | **1406 B** |
| `cert:` | **`<ABSENT>`** | full chain present |
| `auth_attr:` (signedAttrs) | **`<ABSENT>`** | contentType, signingTime, messageDigest |
| Digest | sha512 | sha256 |
| Detached (`d.data`) | `<ABSENT>` — yes | `<ABSENT>` — yes |
| Trailer | `~Module signature appended~\n` | none |

The ~1 KB size difference *is* the certificate. `kmodsign -d` (lowercase)
produces a bare `.p7s` without the module trailer, but it has the same
`cert: <ABSENT>` / `auth_attr: <ABSENT>` core — and LP does not invoke it
anyway.

**Conclusion: no existing Launchpad mode can produce the required signature,
irrespective of how it is delivered.**

`signFit` in full:

```python
def signFit(self, image):
    image_signed = "%s.signed" % image
    ...
    shutil.copy(image, image_signed)
    cmdl = ["mkimage", "-F", "-k", os.path.dirname(key), "-r", image_signed]
```

Anyone reaching for "LP has a FIT mode, use that" will get either a no-op or a
corrupted image.

### Layer 2 — snap builds do not go through archive signing at all

**This is the part that matters, and it corrects a natural assumption.**

`signing.py` lives in `lp/archivepublisher`. It runs on **archive uploads** —
it processes the `raw-signing` tarball produced by a `-signed-` source package
and publishes the results into the archive. A snap built by snapcraft on the
Launchpad build farm never touches that code path: it produces a `.snap` which
goes to the snap store.

So for a kernel snap, the entire `signing.py` mode table is **not reachable**,
regardless of which mode might have the right format. The signing must happen
either:

1. inside the snapcraft build — which needs the private key in the build
   environment (the same problem as the GitHub Secrets approach in the capsule
   PR, and equally unacceptable for a production key), or
2. outside, with the snap build *consuming* a pre-signed artifact.

Option 2 is how this is already solved elsewhere — see the next section.

## 3. The precedent: signatures delivered as a deb

`canonical-kernel-snaps/add-nvidia-lrm` does exactly this:

```sh
apt download linux-signatures-nvidia-$ABI
apt download linux-objects-nvidia-$NVIDIA-$ABI
dpkg-deb --fsys-tarfile ./linux-signatures-nvidia-"$ABI"_*.deb \
  | tar --directory "$CRAFT_PART_INSTALL" --extract ...
```

The pattern:

```
  archive path                          snap path
  ────────────                          ─────────
  -signed- source pkg
        │
        ▼  raw-signing tarball
  Launchpad signing  ────────►  linux-signatures-nvidia-<ABI>.deb
                                         │
                                         ▼  apt download
                                  snapcraft build
                                         │
                                         ▼
                                     kernel snap
```

Signing happens in the archive pipeline, where LP holds the keys; the snap
build merely downloads a deb and extracts the signatures. No private key ever
enters the snapcraft environment.

**This is the shape a production FIT signature should take**, and it is the
same `-generate-`/`-signed-` machinery already being considered for the DTB
capsule. A `linux-signatures-qcom-dtb-<ABI>` deb containing `qclinux_fit.sig`
would slot into `add-nvidia-lrm`'s pattern almost directly.

It does **not** remove the need for a new signing mode — the archive side still
has to produce a detached CMS with embedded certs — but it answers "where does
the signing happen" without putting keys in a snap build.

## 4. Target design: sign before the snap, deliver as a deb

Confirmed direction: **no signing inside snapcraft.** The FIT is signed in the
archive pipeline and delivered to the snap build as a deb, following the
`linux-signatures-nvidia` precedent.

### 4.1 Pipeline

```
linux-qcom  (kernel source package)
      │     builds the kernel, ships DTBs in linux-modules-<ABI>-qcom
      │
      ▼     apt-get download / dpkg-deb -x
linux-generate-qcom
      │     build-dtb-image.sh --soc ... --prune  →  qclinux_fit.img
      │     assemble FAT                          →  combined-dtb.bin
      │     emit raw-signing tarball
      ▼
Launchpad signing
      │     NEW MODE — detached CMS, DER, certs embedded,
      │     signedAttrs, signed with the UEFI / Secure Boot key
      ▼
linux-signed-qcom
      │     download qclinux_fit.sig
      │     mcopy it into combined-dtb.bin
      │     build  linux-signatures-qcom-dtb-<ABI>.deb
      ▼
      published to the archive / PPA
      │
      ▼     apt download   (snapcraft override-build)
dragonwing-kernel snap
```

### 4.2 What the snapcraft part becomes

The whole `combined-dtb` part reduces to a download and an extract:

```sh
apt download linux-signatures-qcom-dtb-$ABI
dpkg-deb --fsys-tarfile ./linux-signatures-qcom-dtb-"$ABI"_*.deb \
  | tar --directory "$CRAFT_PART_INSTALL" --extract ./dtbs/qcom/combined-dtb.bin
```

Gone from the snap build: `openssl`, the snakeoil key, `mcopy`, `mkimage`,
`build-dtb-image.sh`, and the `device-tree-compiler` / `dosfstools` / `mtools`
/ `u-boot-tools` build-packages. No private key ever enters the snapcraft
environment.

### 4.3 Design decision: ship the assembled FAT image, not just the `.sig`

Two options for the deb contents:

| | (a) assembled `combined-dtb.bin` | (b) bare `qclinux_fit.sig` |
|---|---|---|
| Deb size | ~ full DTB set | ~1.4 KB |
| Snap build needs `mtools` | no | yes |
| Snap must rebuild the FIT | no | **yes, byte-identically** |
| Matches nvidia precedent | loosely | literally |

**Recommendation: (a).** Option (b) requires the snap build to reproduce
`qclinux_fit.img` byte-for-byte, or the detached signature simply will not
verify. That is a hard guarantee to hold across two different build
environments and toolchain versions — and the capsule work already turned up a
concrete instance of exactly this class of bug (`XmlFwEntryValidation.py:395`
generates a random `uuid.uuid4()` FFS GUID per build, making `firmware.fv`
non-reproducible; see
`~/qualcomm/ai_effort/capsule_update/launchpad-port-plan.md` section 8.4).

Assemble once, sign, ship the whole artifact. The duplicated DTB bytes are a
cheap price for removing a reproducibility dependency from the critical path.

If (b) is chosen anyway, byte-identical FIT reproduction must be *tested in
CI*, not assumed.

### 4.4 Work items

**`linux-generate-qcom`**
- vendor or depend on `build-dtb-image.sh` and `qcom-metadata.dts`
- build `qclinux_fit.img` from the installed DTBs, assemble the FAT
- emit the raw-signing tarball with the correct extension for the new mode
- extend `parameterise-ancillaries` — it hardcodes
  `f"/boot/{binary}-{abi_version}-{flavour}"` and cannot express a DTB
  directory
- extend `gen-rules` — it only knows how to *copy* one file, not run a build
  step before uploading

**`linux-signed-qcom`**
- `download-signed` to fetch the signature
- `mcopy` the `.sig` into the FAT image
- emit `linux-signatures-qcom-dtb-<ABI>.deb` laying the artifact out at the
  path the snap expects

**Launchpad / lp-signing**
- the new signing mode (section 4.5)

**`carmel-image`**
- replace the `combined-dtb` part's `override-build` with the download+extract
  above
- drop the now-unused build-packages

Note that `-generate-`/`-signed-` for the Qualcomm kernel **do not exist yet** —
they are also a prerequisite for the DTB capsule work, so the two workstreams
share this foundation even though their signing requirements differ.

### 4.5 The new signing mode

Detached CMS, DER, certificates embedded, signedAttrs present, over an opaque
blob — i.e. `openssl cms -sign -binary -outform DER` against LP's existing
UEFI key material, emitting `<name>.sig`.

Possibly implementable as an *output variant* of the existing
`SigningKeyType.UEFI` rather than a new key type, which would avoid the
dual-codebase enum plus DB-migration work described in
`capsule_update/launchpad-port-plan.md` section 3. Needs confirmation from IS /
the lp-signing maintainers.

**This is the only genuine blocker.** Everything in 4.1–4.4 is conventional
packaging work, and the delivery half is already proven in production by
`linux-signatures-nvidia`.

## 5. Contrast with the DTB capsule

| | DTB capsule (`capsule_update/`) | Carmel FIT signature |
|---|---|---|
| Consumer | UEFI capsule update (FMP) | UEFI Secure Boot at boot |
| Trust anchor | `QcCapsuleRootCert`, **fused into the SoC** | UEFI Secure Boot `db` (assumed — see below) |
| Key owner | **Qualcomm** | Canonical (the UKI/SB key) |
| Format gap | yes — new mode needed | yes — new mode needed |
| Key-custody gap | **yes — blocking, needs Qualcomm** | **probably not** |
| Firmware re-provisioning | likely required | probably not |
| Delivery | deb / capsule on the ESP | snap, via a signatures deb |

The capsule is blocked on a *business negotiation*. This one looks blocked only
on *engineering* — the key already exists on the Canonical side and the trust
path already admits the UKI.

That makes it the more tractable of the two, but the two should not be bundled
into one request: they need different signing modes, and conflating them risks
the easier one inheriting the harder one's blocker.

## 6. Open questions

1. **Does the firmware verify `qclinux_fit.sig` against Secure Boot `db`, or
   against a separately provisioned certificate?** The Qualcomm doc
   `80-70020-11` should say. This is decisive: if it is `db`, the key-custody
   advantage in section 5 holds. If it is a separate provisioned cert, this
   becomes capsule-shaped and inherits the same negotiation. **Confirm before
   telling anyone this one is easy.**
2. How is `kernel.efi` (the UKI) signed for production Ubuntu Core kernel
   snaps today? Whatever that mechanism is, the FIT signature should reuse it —
   the snapcraft comment says the keys must match. Nothing in
   `canonical-kernel-snaps` performs signing, so it happens elsewhere.
3. Can lp-signing emit a new output format under an existing `SigningKeyType`,
   or does any new format require a new key type plus DB migrations in both
   codebases?
4. Is `--prune` with a fixed SoC list (`hamoa purwa qcs6490 qcs8275 qcs9075`)
   intended to stay hardcoded in the snapcraft file? It duplicates the
   per-flavour filtering logic the capsule work also needs.

---

## 7. Summary

- The snippet is a **detached CMS signature over the whole FIT blob**, stored
  as a sidecar `.sig` on the FAT image. It is *not* U-Boot FIT signing, despite
  the name.
- It currently uses a **snakeoil test key**; production needs the real UKI /
  Secure Boot key.
- **Launchpad cannot produce this today.** No archive signing mode emits the
  format — verified empirically against `kmodsign`, which strips both the
  certificate chain and the signed attributes — and more fundamentally, snap
  builds do not use the archive signing path at all.
- **Agreed direction:** sign before the snap is built, deliver the signed
  artifact in a deb, and have snapcraft download and unpack it. No signing in
  snapcraft, no key in the build environment. This is the
  **`linux-signatures-nvidia` pattern**, already in production use.
- Ship the **assembled `combined-dtb.bin`** rather than the bare `.sig`, so the
  snap build never has to reproduce the FIT byte-identically (section 4.3).
- The **only real blocker is the new signing mode**. The rest is conventional
  packaging, on top of `-generate-`/`-signed-` packages that the DTB capsule
  work needs anyway.
- Unlike the capsule, the **key custody problem probably does not exist here** —
  pending confirmation of question 1.
