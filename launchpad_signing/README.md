# Launchpad capsule signing

Patches against Launchpad itself. They are kept here rather than in the source
package they serve, because they are changes to Canonical infrastructure and
are not part of any `debian/` tree.

The package that consumes this mode is **`~/qualcomm/linux-signed/`**; the
analysis that led to it is in `../capsule_update/`, principally
`launchpad-port-plan.md`.

Two patches, one per codebase. Both were verified with `git apply --check`
against pristine upstream.

| Patch | Repository | Applies to |
|---|---|---|
| `0001-add-capsule-signing-mode.patch` | `git.launchpad.net/launchpad` | archive publisher: dispatch, local-key path |
| `0002-lp-signing-capsule-key-type.patch` | `git.launchpad.net/lp-signing` | the signing service: key custody and the signing operation |

`0001` alone is enough for local-key signing. `0002` is what makes the mode
work when `PUBLISHER_USES_SIGNING_SERVICE` is set, which is the configuration
that matters for a production archive.

## What the patch does

| File | Change |
|---|---|
| `lib/lp/services/signing/enums.py` | `SigningKeyType.CAPSULE = DBItem(9, ...)` |
| `lib/lp/archivepublisher/signing.py` | `.capsule` extension dispatch, `capsule.key`/`capsule.crt`/`capsule-chain.pem` paths, `signCapsule()`, `generateCapsuleKeys()`, `keyFilesExist` and signing-service suffix wiring |

`signCapsule()` runs:

```
openssl smime -sign -binary -outform DER -md sha256 \
    -signer capsule.crt -inkey capsule.key [-certfile capsule-chain.pem] \
    -in <file>.capsule -out <file>.capsule.sig
```

Two properties matter and neither is available from the existing modes:

* **The certificate chain is embedded.** EDK2 populates its `X509_STORE_CTX`
  from the PKCS#7 blob itself and verifies the result against a single root
  fused into the device. There is no certificate store to look a signer up in,
  so anything not carried inside the signature is unavailable to the verifier.
* **Signed attributes are present.** The verifier expects CMS `SignedData`,
  not a bare signature.

`kmodsign -D sha512`, which `signKmod`/`signOpal`/`signSipl` use, emits
neither — measured on a 2048-bit key over a 4 KiB input it produces 436 bytes
with `cert: <ABSENT>` and `auth_attr: <ABSENT>`, against 1406 bytes with the
full chain and three signed attributes from `openssl cms`. `signUefi` is not
usable either: `sbsign` requires a PE/COFF image and rejects a capsule blob
with `Invalid DOS header magic`. `signFit` runs `mkimage -F -k -r`, which
rewrites the file in place and understands only FIT.

## What the patch deliberately does not do

`generateCapsuleKeys()` raises instead of generating a key.

Every other key type here is safe to autogenerate, because a fresh self-signed
key produces a signature that whoever consumes it was always going to have to
be told about. A capsule is not like that. It is verified before the OS starts
against a root fused into the device, and nothing on the archive side can add
to that store. An autogenerated key would produce capsules that build, publish
and install perfectly and are then silently rejected by every device that
receives them — the worst possible failure mode. Capsule keys have to be
provisioned deliberately.

## The lp-signing side (`0002`)

The private keys and the real signing operation live in a second codebase,
`https://git.launchpad.net/lp-signing`, whose `lp_signing/enums.py` carries a
numerically coupled copy of the enum. `0002` adds:

| Site | Change |
|---|---|
| `lp_signing/enums.py` | `KeyType.CAPSULE = DBItem(9, ...)` — same number as `0001` |
| `Key._getX509Fingerprint` | capsule certs are PEM, so the leaf fingerprints normally |
| `Key.generate()` | explicit refusal, matching `generateCapsuleKeys()` |
| `Key.inject()` | capsule added to the X509 fingerprint group, so injection works |
| `Key.sign()` | new `DETACHED` branch emitting DER CMS with the chain embedded |

### The chain fits the existing schema

The obvious objection to this mode is that lp-signing stores exactly two blobs
per key — `private_key` and `public_key` — and a capsule signature needs a
third thing, the intermediates. It turns out no schema change is required.

The chain rides in the certificate slot as a **PEM bundle, leaf first**, and
`sign()` splits it. Two measured facts make that safe:

* `_getX509Fingerprint` pipes the slot into `openssl x509 -noout -fingerprint`,
  which reads only the first certificate in a PEM stream. A bundle therefore
  fingerprints identically to the leaf alone — verified, both give
  `D5:17:00:58:F4:30:...`. Key identity is unaffected.
* Splitting at sign time avoids a duplicate. Passing the bundle as both
  `-signer` and `-certfile` does work and does verify, but embeds the leaf
  twice (2861 bytes against 2153). The patch splits instead, giving exactly
  leaf + intermediates.

So this is an additive patch: no migration, no new column, no new API field.
`inject_key` already carries a `public-key` blob and does not care what is in
it.

### What provisioning then looks like

Assuming the key and its certificates are supplied, the flow is:

1. Concatenate the issued leaf and the intermediates into one PEM, leaf first.
   Do **not** include the root — the device already has it, and sending it
   wastes capsule space.
2. `POST /inject` with `key-type: CAPSULE`, the private key, and that bundle.
3. Authorise the archive's client against the key.

`Key.generate()` refuses for CAPSULE, so there is no path by which an archive
silently ends up with a self-signed capsule key instead.

### What is still an open question

Not the mechanism any more — the **custody policy**. Specifically:

* Is Canonical willing to hold a third-party private key that can sign
  firmware for that party's devices, and under what controls? lp-signing does
  have an HSM path, but at the revision read here it is UEFI-only
  (`_is_uefi_hsm_key`, `_UEFI_HSM_SIGN`), so a capsule key would be
  software-backed unless that is extended.
* Leaf or intermediate? If Qualcomm issues a **leaf**, every rotation is a
  round-trip to Qualcomm. If they issue an **intermediate CA**, Canonical can
  mint and rotate its own leaves. Worth asking for the intermediate.
* Validity and revocation. Pre-OS verifiers commonly ignore `notAfter`, but
  not universally, and there is no revocation path at all before the OS
  starts. Expiry behaviour should be confirmed against real firmware rather
  than assumed.

## A constraint on whatever certificate gets issued

Found while building the interim test chain in
`~/qualcomm/linux-signed/debian/capsule/test-keys/`, and worth stating before
anyone requests a certificate from Qualcomm.

**The signing certificate must not carry an `extendedKeyUsage` that excludes
`emailProtection`.** An EKU of `codeSigning` — the intuitive choice for a
firmware signing cert — makes verification fail outright, before the signature
is even examined:

```
PKCS7_verify:certificate verify error:Verify error: unsuitable certificate purpose
```

The reason is that EDK2's `Pkcs7Verify()` calls OpenSSL's `PKCS7_verify()`,
which applies the S/MIME signing purpose to the chain. `purpose_smime()`
rejects any certificate whose EKU is present but lacks the S/MIME bit. EDK2
sets `X509_V_FLAG_PARTIAL_CHAIN` and `X509_V_FLAG_NO_CHECK_TIME`, neither of
which disables the purpose check.

Omitting the extension entirely satisfies it, because the check only rejects
an EKU that *is* present. The test chain therefore ships a leaf with
`basicConstraints=CA:FALSE` and `keyUsage=digitalSignature` and no EKU at all,
which was confirmed to verify.

This is worth raising with Qualcomm explicitly: a certificate that looks
correct to a PKI team can be one that no device will accept, and the failure
happens at verification time on hardware rather than anywhere in the build.

## Reuse

Nothing in the mode is capsule-specific. It signs an opaque blob and returns a
detached CMS signature with a chain — which is also exactly what the Ubuntu
Core FIT signing work needs (see `~/qualcomm/ai_effort/core_fit_signing/`).
One mode covers both; the format knowledge stays in the packages.
